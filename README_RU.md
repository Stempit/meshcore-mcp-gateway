# meshcore-mcp-gateway 🎙️📡

**MCP-шлюз к вашей mesh-рации. Говорите с ней. В прямом смысле.**

meshcore-mcp-gateway подключает ИИ-агентов к LoRa-станции MeshCore по протоколу
MCP (Model Context Protocol). Спросите у колонки
[XiaoZhi](https://xiaozhi.me) на столе: *«есть новые сообщения в mesh?»* — и
она их зачитает; скажите *«ответь Wire: уже иду»* — и сообщение уйдёт в
радиоэфир. Те же инструменты работают у любого MCP-хоста —
[nanobot](https://github.com/nanobot-ai/nanobot),
[Hermes Agent](https://github.com/NousResearch/hermes-agent), Claude,
вашего собственного агента — с одного шлюза и одной рации.

Это **самостоятельная фича**: шлюз сам открывает соединение с устройством
MeshCore (BLE или USB-serial, секция `Connection`) и больше ни в чём не
нуждается — ни в HTTP-шлюзе, ни в боте.

## Транспорты

Один процесс обслуживает любую комбинацию трёх MCP-транспортов:

| Транспорт | Направление | Для чего |
|---|---|---|
| `MCP` (xiaozhi.me) | исходит наружу по WebSocket | голосовые ассистенты XiaoZhi через MCP access point |
| `Transports.http` | входящий Streamable HTTP | nanobot, Hermes, любой MCP-хост, которому нужен URL |
| `Transports.stdio` / `-stdio` | stdin/stdout | хосты, запускающие шлюз как подпроцесс |

Со стороны XiaoZhi — исходный трюк, направление соединения:

```
[Устройство XiaoZhi] ⇄ ws ⇄ [облако xiaozhi.me] ⇐= исходящий wss =⇐ [meshcore-mcp-gateway]
                                                                        ⇅ BLE/serial
                                                                   [устройство MeshCore]
```

Шлюз **сам дозванивается** до xiaozhi.me и на этом соединении работает как
MCP-сервер — облако выступает MCP-клиентом. Соединение исходящее, поэтому всё
работает за NAT провайдера, за CGNAT, за файрволом: без проброса портов, без
белого IP, без туннелей. (Тот же механизм access point используют
XiaoZhi-интеграции.)

Обычные агенты подключаются как привыкли — шлюз выступает сервером:

```
[nanobot / hermes / любой MCP-хост] ⇒ HTTP POST /mcp ⇒ [meshcore-mcp-gateway]
                                                          ⇅ BLE/serial
                                                    [устройство MeshCore]
```

У каждого подключённого клиента — **свой курсор чтения** (по имени, которое
клиент называет в `initialize`): hermes, вычитавший инбокс, не прячет
сообщения от XiaoZhi, а переподключившийся клиент продолжает с того же места,
ничего не перечитывая. Отправки делят одну рацию и сериализуются драйвером
устройства.

## Что умеет агент

| Инструмент | Пример голосовой команды | Что делает |
|---|---|---|
| `mesh_get_new_messages` | *«прочитай новые сообщения»* | Зачитывает непрочитанные mesh-сообщения (по 10 за вызов, с долистыванием) |
| `mesh_send_message` | *«отправь Короеду: буду через час»* | Отправляет личное сообщение или сообщение в канал |
| `mesh_search_contacts` | *«найди контакта Йорика»* | Ищет контакты по фрагменту имени (регистр и эмодзи не важны) — так агент находит адресатов в большом списке |
| `mesh_list_contacts` | *«кто есть в сети?»* | Перечисляет первые известные имена узлов — для небольших списков |
| `mesh_list_channels` | *«какие каналы есть?»* | Перечисляет настроенные каналы |

Ошибки инструментов возвращаются человекочитаемым текстом («получатель не
найден — проверьте имя через mesh_list_contacts»), так что агент объяснит, что
пошло не так, а не промолчит.

## Настройка

**1. Устройство.** Настройте, как достать до компаньона MeshCore (общее для
всех транспортов):

```yaml
# config.yaml (подмножество семейного формата; лишние секции игнорируются)
Connection:
  type: "bt"             # "bt" (BLE, по умолчанию) или "serial"
  # serial_port: "/dev/ttyUSB0"
  # serial_baud: 115200
  channel_transmissions: 3

Shrink:                  # как исходящие сообщения подгоняются под эфир
  cyr_to_lat: true       # сжатие кириллицы в визуально идентичную латиницу
  # max_bytes: 140       # жёсткий лимит эфира
  #   xiaozhi: split     # голосовой путь и так делит по умолчанию
```

**2. Хотя бы один транспорт** (см. ниже). Без единого шлюз откажется
запускаться.

**3. Запуск:** `go run .` (или бинарник; `-config` указывает другой файл
конфигурации).

### Транспорт: XiaoZhi

Получите URL точки подключения MCP: зайдите в
[консоль xiaozhi.me](https://xiaozhi.me) → откройте своего агента (智能体) →
найдите **MCP 设置 / 获取 MCP 接入点** и скопируйте URL
(`https://api.xiaozhi.me/mcp/?token=…`). Точка привязана к конкретному
агенту: инструменты появятся у этого агента.

```yaml
MCP:
  endpoint_url: "https://api.xiaozhi.me/mcp/?token=XXXX"
```

Индикатор MCP в консоли должен позеленеть через несколько секунд. Дальше
просто разговаривайте с устройством XiaoZhi.

### Транспорт: HTTP — nanobot, Hermes, любой MCP-хост

```yaml
Transports:
  http:
    enabled: true
    # listen: "127.0.0.1:8788"   # по умолчанию; для loopback токен не нужен
    # path: "/mcp"               # по умолчанию
    # token: "общий-секрет"      # обязателен для не-loopback-адреса
```

Затем подключите шлюз в конфиге своего хоста:

```yaml
# Hermes Agent (~/.hermes/config.yaml; точные ключи вашей версии —
# в документации Hermes про MCP):
mcp_servers:
  meshcore:
    url: "http://127.0.0.1:8788/mcp"
    headers:
      Authorization: "Bearer общий-секрет"
```

```yaml
# nanobot (nanobot.yaml):
mcpServers:
  meshcore:
    url: "http://127.0.0.1:8788/mcp"
    headers:
      Authorization: "Bearer ${MESHCORE_TOKEN}"
```

Хостов может быть несколько одновременно — у каждого свой курсор сообщений.

**Доступ извне localhost:** для не-loopback-адреса `listen` без `token` шлюз
откажется стартовать. Встроенного TLS нет — для доступа по сети ставьте шлюз
за Tailscale, SSH-туннель или reverse proxy.

### Транспорт: stdio

Для хостов, запускающих шлюз как подпроцесс (stdio MCP-сервер):

```json
{
  "command": "/path/to/meshcore-mcp-gateway",
  "args": ["-config", "/path/to/config.yaml", "-stdio"]
}
```

Кадры — построчный JSON-RPC на stdin/stdout; логи идут в stderr. Флаг
`-stdio` можно совместить и с другими транспортами. Помните про правило
«одно приложение на устройство» ниже: не давайте каждому агенту плодить свой
экземпляр на одну рацию — лучше один шлюз с HTTP, а агенты ходят в него.

### Параметры конфигурации

| Ключ | По умолчанию | Значение |
|---|---|---|
| `MCP.endpoint_url` | *(опционален)* | URL точки подключения MCP из консоли xiaozhi.me (исходящий WebSocket) |
| `Transports.http.enabled` | `false` | Раздавать инструменты по Streamable HTTP |
| `Transports.http.listen` | `127.0.0.1:8788` | Адрес привязки; не-loopback требует `token` |
| `Transports.http.path` | `/mcp` | Путь MCP-эндпоинта |
| `Transports.http.token` | — | Bearer-токен, который предъявляют клиенты |
| `Transports.stdio.enabled` | `false` | Построчный JSON-RPC на stdin/stdout (также флаг `-stdio`) |
| `Output.max_message_runes` | `200` | Обрезка каждого сообщения в `mesh_get_new_messages` — увеличьте для текстовых агентов |
| `Connection.*` | — | К какой станции MeshCore подключаться и как |
| `Shrink.*` | для голоса — `split` | Подгонка исходящих сообщений — см. «Детали поведения» |

Флаги: `-config <путь>` (по умолчанию `./config.yaml`), `-stdio`.

### Одно приложение на устройство

Шлюз подключается к компаньону напрямую. Не запускайте его на **том же
физическом устройстве**, что [meshcore-go-bot](https://github.com/stempit/meshcore-go-bot)
или [HTTP-шлюз](https://github.com/stempit/meshcore-http-gateway)
одновременно — MeshCore-компаньон обслуживает одно BLE/serial-соединение.
Разные устройства — пожалуйста. Внутри одного процесса шлюза рацию делят
сколько угодно агентов — для того всё и задумано.

## Детали поведения

- **Отправки подгоняются под эфир.** Исходящие сообщения проходят через тот
  же пакет `fit` (из [meshcore-kit](https://github.com/stempit/meshcore-kit)),
  что и все отправки бота. По умолчанию сообщение длиннее лимита эфира
  **делится** на части с маркерами `[i/N]`, которые уходят одна за другой
  (каждая — до ~30 с эфира). С `Shrink.cyr_to_lat: true` кириллица сначала
  сжимается в визуально идентичную латиницу — это экономит байты. Стратегию
  можно переопределить: `Shrink.overrides.xiaozhi` (`truncate`, `split`,
  `skip`).
- **Русский находит английские имена.** Сопоставление контактов —
  фонетическое и не зависит от языка: запрос *«Йорик»* — и поиск, и отправка
  найдут `Yorick 💀` (и наоборот: латинское написание найдёт `Короед`).
  Сначала пробуется точное имя, затем игнорируются регистр, эмодзи и
  пунктуация, и лишь потом включается фонетический нечёткий поиск с небольшим
  бюджетом правок. Если подходят несколько контактов сразу, агент получит
  список кандидатов и попросит полное имя.
- **Курсоры на каждого клиента.** При первом подключении курсор клиента
  ставится на самый свежий ID инбокса — «новые сообщения» значит *пришедшие с
  этого момента*; накопленный до подключения бэклог не перечитывается.
  Курсор переживает переподключения (ключ — `clientInfo.name`, названное
  клиентом); перезапуск шлюза начинает всех с чистого листа.
- **Медленная отправка — это нормально.** Подтверждение доставки по радио
  занимает до ~30 секунд; `mesh_send_message` ждёт столько, и агент
  подтверждает с паузой.
- **504 ≠ потеряно.** Отправка без радиоподтверждения возвращается как
  «передано, но не подтверждено — возможно, ещё дойдёт»; не повторяйте её
  вслепую — ретраи радио могут всё-таки донести.
- **Автопереподключение**, в обе стороны: к xiaozhi.me (экспоненциальная
  задержка, 2 с → 60 с) и к BLE-устройству (периодическая статистика как
  сторожевой таймер). Связь с xiaozhi.me удерживается WebSocket-пингами
  каждые 30 с — паузы между голосовыми командами иначе приводят к обрыву по
  таймауту простоя на NAT или балансировщике (close 1006); канал без понга
  считается умершим через 90 с.

## Карта кода

`main.go` (корень композиции + конфиг), `gateway/server.go`
(JSON-RPC/MCP-протокол + реализация инструментов, по-клиентский `Conn`),
`gateway/xiaozhi.go` (исходящий WebSocket и переподключение),
`gateway/http.go` (транспорт Streamable HTTP), `gateway/stdio.go`
(stdio-транспорт), `gateway/mesh.go` (интерфейс `Mesh` + прямой бэкенд к
устройству), `gateway/tools.go` (описания инструментов). Рантайм устройства
(подключение, стартовая синхронизация, инбокс, keepalive) — из
[meshcore-kit](https://github.com/stempit/meshcore-kit); драйвер
протокола — [meshcore-go](https://github.com/stempit/meshcore-go).
